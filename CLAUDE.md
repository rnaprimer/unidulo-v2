# Unidulo v2

Unidulo is a managed B2B manufacturing platform in India, starting with custom
packaging. This repo is a from-scratch rebuild. The old repo (`rnaprimer/unidulo`)
and its Supabase project are archived: do not read from, write to, or migrate them.

The owner is a solo founder who is not writing the code but wants to understand it.

## Scope of v1 (build only this)

1. Marketing site: home, how it works, packaging, for manufacturers, contact.
2. Packaging RFQ form: multi-step, text only, no file uploads.
3. Manufacturer interest form.
4. Email alert to the owner for every submission.

## Out of scope until the owner asks

File or artwork uploads, user accounts and login, customer or manufacturer
portals, operator dashboard, supplier matching, quotations, orders, payments,
production tracking, analytics, AI features, background queues, Redis.
Do not add scaffolding, tables, or placeholder pages for any of these.

## Stack

- Next.js (App Router) with TypeScript and Tailwind CSS
- Supabase PostgreSQL (a new project, not the old one)
- Zod for validation, one schema shared by client and server
- Cloudflare Turnstile for bot protection
- Resend for email (called with fetch, no SDK)
- Vitest for tests (Playwright not added yet)
- Hosted on Vercel, deployed from `main`

Do not add other dependencies without asking first.

## Engineering rules

- The server is the source of truth. Client validation is a convenience only.
- All database writes happen server-side. The Supabase service-role key never
  reaches the browser.
- Row Level Security is on for every table, with no public policies.
- Schema changes go in SQL migration files in the repo, never ad hoc in the
  dashboard.
- RFQ reference numbers are generated by the database, not the browser.
- A repeated or double-clicked submit must not create two RFQs.
- Save the RFQ first, then send the email. A failed email must not lose the RFQ
  or show the customer an error; log it so it can be resent.
- Verify the Turnstile token on the server. Add a honeypot field and a basic
  per-IP rate limit.
- Never show a success message unless the database write succeeded.
- No fake data on the site: no invented customers, supplier counts, testimonials,
  or production statuses.
- Secrets live in `.env.local` and Vercel environment variables. Never commit them.
  Keep `.env.example` up to date.

## Data model for v1

Two tables only: `rfqs` and `manufacturer_applications`.

RFQ fields: packaging type, intended use, length, width, height, unit, material,
print colours, finishing, quantity, delivery city and state, required-by date,
notes, contact name, company, email, phone, reference number, status, created_at.
Use constraints (NOT NULL, CHECK, enums) rather than trusting the application.

## Build order

0. Scaffold the app and deploy the empty site to Vercel.
1. Marketing pages and shared layout.
2. Supabase schema, migrations, and RLS.
3. RFQ form end to end.
4. Turnstile, honeypot, rate limit.
5. Email alert via Resend.
6. Manufacturer interest form.
7. Tests, then production launch.

Finish and verify one milestone before starting the next.

## How to work with the owner

- Before each milestone, state the plan in a few plain sentences and wait for a go.
- After each milestone, give a short summary: what was built, which files matter,
  and one concept worth understanding, explained for someone new to it.
- Keep code simple and readable over clever. Prefer fewer files and fewer
  abstractions.
- When the owner must do something by hand (create a Supabase project, get an
  API key, set a Vercel variable), give exact click-by-click steps.
- Say plainly what was tested and what was not. Never claim something works in
  production without checking the deployed site.

## Ask before doing any of these

- Running migrations against the hosted Supabase project
- Sending real emails
- Changing DNS or the unidulo.com domain
- Anything that costs money
- Deleting data or force-pushing

## Brand and tone

Name is Unidulo (never the old name Monobloc). Look: professional, minimal,
industrial but approachable. Copy: plain language, no jargon, and no claims
about capabilities that are not live. Low MOQ is one benefit, not the headline.
